ITM分析ツール 引継ぎ資料
（最終更新: 2026-09-25）

====================================================================
1. これは何か
====================================================================
米国株のティッカーを入力すると、過去の株価データから「オプションの権利行使
価格に対してどれくらいの確率でITM（In The Money）になったか」を、プット売/
コール売/コール買/プット買の4タイプについて計算・表示するWebツール。

きっかけは、ユーザーが個人で使っていたExcel（Googleファイナンス関数ベース）
のITM分析シートをWeb化したいという相談から始まった。スプレッドシートでは
なく、誰でもブラウザでティッカーを打てば見られるツールとして新規に作った。

公開URL: https://itm-bunseki.pages.dev
リポジトリ: https://github.com/notenki0909-hub/itm-bunseki （GitHub連携で
Cloudflare Pagesにauto-deploy。mainブランチにpushすると自動反映）
ローカルの作業フォルダ: C:\Users\noten\Documents\VisionCreator\AI道場\ITM分析ツール

2. 技術構成
====================================================================
- 素のHTML + CSS(1枚) + Vanilla JS(ESモジュール)。フレームワーク・ビルド
  ステップなし。Cloudflare PagesのGit連携でmain push即デプロイ。
- functions/api/history.js … Cloudflare Pages Functions。Twelve Data API
  への中継プロキシ（ブラウザCORS回避・APIキー隠蔽が目的）。
- Cloudflare KV（PRICE_CACHE）でサーバー側キャッシュ。世界中のCloudflare
  拠点で共有されるグローバルキャッシュ。
- データ提供元: Twelve Data 無料プラン（800 credits/日、8 req/分、米国株
  のみ対応で足りている）。

【重要】Cloudflare Pagesの設定は2箇所に分かれている。混同しないこと。
  - KVなどのbindingsは "wrangler.toml" で管理（ダッシュボードからは設定
    できない）。コミット・pushすれば反映される。
  - APIキーなどのSecretsは Cloudflareダッシュボードの
    Settings → Variables and secrets からのみ設定できる。

構成ファイル:

3. データ取得・キャッシュ設計（重要な設計方針）
====================================================================
- 1つのティッカーの価格データは、分析ボタンを押したタイミングで「1回だけ」
  取得する。以降、取引タイプ/比率/判定期間/集計期間/エントリー条件などを
  変更しても再取得はせず、取得済みデータをブラウザ内でJSにより再計算する
  だけ（無駄なAPI呼び出しを絶対に発生させない、というのが終始一貫した要件）。
  この原則は詳細マトリクスページ単体（後述）にも同様に適用されている。
- ブラウザ内メモリ(priceCache)で同一銘柄の重複取得を防止。複数タブで同じ
  銘柄を開いても実リクエストは1回。詳細マトリクスページも独自のpriceCache
  を持つ（別ページ/別モジュールのため分析ページとは共有しないが、KVキャッシュ
  のおかげでサーバーへの実アクセスは軽い）。
- サーバー側もCloudflare KVで20時間キャッシュ。複数人が同時に使っても
  「同一銘柄への実アクセスは概ね1日1回」に抑えられる設計。
- 詳細マトリクスページへの遷移は「同一タブ内」で行い（別タブは開かない）、
  sessionStorage経由で渡すのは軽量な設定（レシピ）のみ。価格データそのもの
  は渡さず、詳細マトリクス側で改めて取得する（KVキャッシュがあるので軽い）。
  以前は価格データを丸ごと渡していたが、詳細マトリクス側でも銘柄・条件を
  変更できるようにした際にこの設計へ変更した（DETAIL_HANDOFF_KEY =
  "itm-detail-handoff"）。

====================================================================
4. 主な機能
====================================================================
- ティッカー入力 → 4タイプ（プット売/コール売/コール買/プット買）ごとの
  ITM確率分析。判定期間(10/20/30/60/90/120/150営業日)・集計期間(6ヶ月〜3年)・
  権利行使価格の比率を指定可能。
- 複数タブでティッカー/タイプを切り替えて比較可能。
- 状態の永続化: localStorage（STORAGE_KEY = "itm-tool-state-v1"）に
  タブ構成・入力値を自動保存し、閉じて再度開いても続きから再開できる。
- 共有リンク: URLクエリパラメータ "share" に軽量な設定情報（ティッカー・
  タイプ・比率・判定期間等の「レシピ」のみで、価格データそのものは含め
  ない）をJSON化して埋め込み、別端末でも同じ設定を開ける。受け取り側は
  KVキャッシュのおかげで再取得コストが低い。
- エントリー条件で絞り込み: 過去の値動き条件でエントリー日をさらに絞り込む
  機能。「N営業日前と比較」「直近7営業日中の該当日数」の2方式を選べる
  （詳細は8章）。
- 詳細マトリクス（別ページ、元Excelのヒートマップ形式を再現）: ページ自体
  が独立した分析フォームを持ち、分析ページを経由せず単体でも使える
  （詳細は5章）。
- 配色テーマ: ライト/ダーク × 7アクセントプリセット。localStorageキー
  "pp_theme" を使っており、これは同じ作者の「銘柄診断ツール」と共有の
  仕組み（そちらのテーマ設定がこちらにも反映される）。
- 総合判定バッジ・「過去の営業日ごとのITM確率」チャート・「エントリー日
  ごとのITM状況」ヒートマップは、それぞれ異なる配色ロジックを持つ
  （詳細は6章。3つとも同じ配色にした時期があったが、最終的に用途に応じて
  使い分ける設計に落ち着いた）。

5. 詳細マトリクスページの機能拡張
====================================================================
初期実装では「分析ページで分析した内容をそのまま別タブで表示するだけ」
だったが、以下の機能拡張を経て、詳細マトリクスページ単体で完結する設計に
なっている。

- ページ自体に分析フォーム（ティッカー・取引タイプ・権利行使価格の比率・
  判定期間・集計期間・「表示する」ボタン）を持つ。分析ページの「詳細マト
  リクスを別ページで見る」から開いた場合は自動でその設定が反映されるが、
  詳細マトリクスページを直接開いてゼロから使うこともできる。
- 開き方: 別タブではなく同じタブ内で遷移する（window.location.href。
  以前はwindow.open("_blank")で新規タブを開いていたが、ユーザーの要望で
  変更した）。
- 判定期間は最大150営業日まで選択可能（WINDOW_OPTIONSに120/150を追加）。
  列数が多くなるため、31日後以降の列は初期状態で折りたたまれており、
  「▼ 31日後以降を表示（◯列）」という枠線付きボタン（.btn-outlineクラス。
  最初は文字リンクスタイルで目立たず分かりにくいという指摘を受けて変更）
  をクリックすると展開できる。
- 横スクロールは表専用のdiv内(overflow-x:auto)ではなく、ページ全体
  (.dm-table-wrap自体はoverflow指定なし)からはみ出させる方式にしている。
  行数が多いと表の中だけでスクロールさせると横スクロールバーが画面の
  一番下まで見に行かないと出てこず使いづらい、という指摘を受けての変更。
  ブラウザウインドウ自体の横スクロールバー（常に画面下部にある）でスクロー
  ルできる。
- 表示するエントリー日数は「集計期間 − 判定期間」ではなく、集計期間の
  全日を表示する（以前は判定期間分を差し引いていたが、直近のデータが
  足りない末尾の日も見たいという要望で変更）。判定期間分のデータがまだ
  確定していない先読みセルやITM日数(30日以内)セルは、無地ではなく
  はっきりしたグレー（.dm-nodata / classifyBefore・classifyAfterがnullの
  ときに返すクラス）で「データなし」と分かるようにしている。
- 元Excelに合わせて「終値」「権利行使価格」「ITM日数(30営業日以内、判定
  期間の選択に関わらず固定30日基準)」の列を追加している。
- 「表示する」ボタンは集計期間のすぐ右（通常のフォームの並び）。
  「← 分析ページへ戻る」リンクは、1段下にある「標準に戻す」の真上（右端が
  一致）になるよう、js/detail.jsのalignBackLink()で実測して位置合わせして
  いる（ボタンの右端に合わせようとするとページタイトルと重なって折り返す
  問題があったため、この位置に変更した経緯がある）。

6. 配色ロジック（詳細マトリクス／総合判定バッジ／チャート／ヒートマップ）
====================================================================
この節は会話の中で何度も仕様変更が入り、かつ「3つの見た目を統一する→
やっぱり別基準に分ける」という一往復があった、最も間違えやすい箇所。
今後この部分を触る際は必ずこの章を読むこと。

--------------------------------------------------------------------
6-1. 詳細マトリクスの「先読み(N日後)」セルの配色（最終仕様・確定）
--------------------------------------------------------------------
- セルに表示する数値（ツールチップの「権利行使価格比 ±X.X%」）は、常に
  「株価 ÷ 権利行使価格 − 1」の生の値（rawFwd）。符号の変換は一切しない。
  ＋なら株価が権利行使価格より上、－なら下、という直感通りの意味。
- 色は「そのタイプの元Excelシート（プット売/コール売/コール買/プット買の
  各シート）の条件付き書式ルールを実際に解析して抽出した、タイプごとに
  異なるしきい値」で7段階に色分けしている。赤→オレンジ→黄→塗りなし
  （グレー）→水色→青→紫の7色で、赤に近いほど有利、紫に近いほど不利。
    プット売: +40/+30/+20/+5/0/-5% を境に 赤/オレンジ/黄/塗りなし/水色/青/紫
    コール売: -30/-20/-10/-5/0/+5% を境に 赤/オレンジ/黄/塗りなし/水色/青/紫
    コール買: +30/+20/+10/0/-10/-20% を境に 赤/オレンジ/黄/塗りなし/水色/青/紫
    プット買: -30/-20/-10/0/+10/+20% を境に 赤/オレンジ/黄/塗りなし/水色/青/紫
  実装: site/js/detail.js の AFTER_BANDS（typeKeyごとのしきい値テーブル）。
  CSS変数 --gradRed/--gradOrange/--gradYellow/--gradLightBlue/--gradBlue/
  --gradPurple（site/css/style.css の :root）を参照。
- 集計期間の末尾など、先読み先のデータがまだ確定していないセルはnullを
  返し、classifyAfter()がnullなら空色クラス（.dm-nodata、グレー表示）に
  なる。
- 「前営業日比」（エントリー日より前の値動き）の色は上記とは無関係で、
  日本の株価チャート慣習に合わせ「上昇＝赤、下落＝青」で固定（U1=赤、
  D0〜D2=青）。ここは変更していない。

  【経緯（今後同じ勘違いをしないためのメモ）】
  この仕様に至るまでに何度も変更が入っている。
  1. 「有利方向を正として符号反転した値」をそのままツールチップに表示
     （バグ: OTM側なのに+表示になり誤解を招いた）
  2. 表示を生の乖離率(rawFwd)に戻し、色を「ITM側=赤、OTM側=青」に変更
     （誤り: コール売の一例だけを根拠に一般化してしまった）
  3. 4タイプすべてについて「株価がどちらに動いてほしいか」を確認し、
     「そのタイプにとって有利な方向=赤」の2色(赤/青)濃淡グラデーションに
     統一
  4.（最終）ユーザーから「エクセルデータにある色分けに合わせて」という
     要望を受け、元Excelファイルの実際の条件付き書式XMLをopenpyxlで解析
     し、上記の7色・タイプ別しきい値に置き換えた。2色グラデーションでは
     元Excelの配色（赤〜紫の7色）を再現できていなかったため。
  → 教訓: 「有利/不利」の一般論だけでなく、実データ（この場合は元Excel
    ファイルそのもの）が参照できるなら早めに直接解析するほうが手戻りが
    少ない。

6-2. 総合判定バッジの配色（2026-09-25更新: 売り系のしきい値・ラベルを変更）
--------------------------------------------------------------------
- ITM発生エントリー数の割合を「そのタイプにとって有利な方向への確率
  （favorableProb）」に変換し、7段階のしきい値で判定。0=最も有利(激熱)〜
  6=最も不利(大ピンチ)。
  → オプション売りは「利益は限定的・損失は相対的に大きい」非対称な構造
    のため、勝率50%は「コイントスに近い」レベルであり、最下位ランクに
    なるよう意図的にしきい値を高めに設定している。
- 【重要】しきい値・ラベルは売り系/買い系で別々（2026-09-25にユーザーから
  「勝率は最低85%は欲しい」という基準で売り系だけ厳しくしてほしいという
  要望があり変更。以前は売り/買い共通の単一しきい値だった）。
  calc.jsの BADGE_PROB_THRESHOLDS が {sell:[...], buy:[...]} のオブジェクトに
  なり、favorableProbToLevel(favorableProb, group) が group引数でどちらの
  しきい値を使うか切り替える。
    売り(sell): [0.95, 0.90, 0.85, 0.80, 0.70, 0.60]
      ラベル: 激熱/熱/好機/可もなく不可もなく/ひやひや/ピンチ/大ピンチ
      （「ITM」ラベルは廃止し、60%未満を一律「大ピンチ」に統合）
    買い(buy):  [0.95, 0.85, 0.75, 0.65, 0.55, 0.50]（変更なし）
      ラベル: 激熱/熱/好機/ITM/OTM/ピンチ/大ピンチ
  検討の経緯: ユーザーから何度か細かい調整依頼があり、最終的に
  「好機(85-90%)を再導入しつつ、ITMラベルを廃止して60-70%をピンチに
  統合する」という形で7段階を維持する着地になった（8段階になりかける
  提案もあったが、7色パレットの制約を説明し7段階に収める案で合意）。
- 色は6-1と同じ7色（赤→オレンジ→黄→グレー→水色→青→紫）。実装は
  calc.jsのfavorableProbToLevel()（badgeLevelとして0〜6を返す）+
  style.cssの .badge.b0〜.badge.b6。色そのもの（b0〜b6とレベルの対応）は
  変更していない。
- バッジのすぐ下に、選択中の取引タイプのラベル付きの凡例を表示する
  （app.jsのrenderBadgeLegend()）。
- guide.htmlの「総合判定バッジの見方」に、有利方向の確率の算出方法（売り
  は1−割合、買いはそのまま）と、売り用/買い用それぞれの7段階しきい値表を
  掲載している（以前は共通の1つの表だったが、しきい値が別々になったため
  分割した）。

6-3. 「過去の営業日ごとのITM確率」チャート・「エントリー日ごとのITM状況」
     ヒートマップの配色（最終仕様・確定）
--------------------------------------------------------------------
バッジと違い、こちらは「絶対値」を売り/買いそれぞれ専用のしきい値で色分け
している（favorableProbのような有利方向への変換は行わない）。

  チャート（その日のITM率、site/js/chart.js の DAY_PROB_BANDS）:
    売り（プット売/コール売）: 5%以下=水色 / 5〜10%=青 / 10%超=紫
    買い（コール買/プット買）: 10%未満=薄いグレー / 10〜20%=薄い黄色 /
                                20〜30%=オレンジ / 30%以上=赤

  ヒートマップ（判定期間内のITM日数、site/js/heatmap.js の
  ENTRY_HEATMAP_BANDS）:
    売り: 0日=薄いグレー / 1〜3日=薄い水色 / 4〜5日=水色 / 6〜7日=青 /
          8日以上=紫
    買い: 0日=水色 / 1日=薄い水色 / 2〜4日=薄いグレー / 5〜9日=薄い黄色 /
          10〜14日=オレンジ / 15日以上=赤

  【経緯（今後同じ勘違いをしないためのメモ）】
  1. 元々はチャート・ヒートマップともに「ITM率/日数が高い=赤(悪い)」を
     売り/買い問わず一律に使っており、買いタイプでは実際の有利/不利と
     色が逆転していた（バグ）。
  2. ユーザー指摘を受け、バッジと同じ「favorableProbベースの7段階配色」に
     統一（総合判定・チャート・ヒートマップの3つが完全に同じロジックに
     なった時期がある。この時のコミットはa4f5cad）。
  3. しかし実際に使ってみると、チャートやヒートマップは値の分布が偏る
     （例: 買いタイプで序盤の日は常にITM率が低く、favorableProbベースだと
     ほぼ全部同じ色になり情報量がなくなる）ため、ユーザーから「グループ
     ごとの生の値（絶対値）」で色分けし直してほしいという要望が入り、
     バッジとは別ロジックに戻した（5c1dd8e→a952345で現在の形に）。
  → 教訓: 「見た目の配色ルールを揃える」ことと「その配色ルールが実際の
    分布に対して情報量を持つか」は別問題。集計値（バッジ、母集団全体に
    対する確率）と個別値（チャートの1日ごと、ヒートマップの1エントリー
    ごと）とでは、同じ配色ロジックが必ずしも適切とは限らない。

  凡例はグラフのすぐ下に表示（app.jsのrenderColorLegend()、DAY_PROB_BANDS
  /ENTRY_HEATMAP_BANDSをそのまま参照して生成、取引タイプで自動的に切替）。
  「過去の営業日ごとのITM確率」チャートのタイトルクリック、「エントリー日
  ごとのITM状況」タイトルクリックでも同じ説明が表示される（setupStatExplain
  の対象セレクタに.chart-title[data-target]を追加して実現）。

9-1. 基本設計
--------------------------------------------------------------------
- 「取引の種類」プルダウンは、上部の「取引タイプ」に連動して単体/スプレッド
  の2択に絞られる（プット売→プット売り/ブルプット、コール売→コール売り/
  ベアコール、コール買→コール買い/ブルコール、プット買→プット買い/
  ベアプット）。RISK_VARIANT_LABELS（calc.js）とinitRiskRewardVariantOptions
  （app.js）で実装。
- 「ITM日数のしきい値(◯日以上)」（初期値4）以上ITMだったエントリー日を、
  売りは「負け」・買いは「勝ち」とみなして勝率を算出する
  （computeWinRateByItmDays、calc.js）。ITMは買い手に有利・売り手に不利、
  という向きは本ツール全体で一貫している。
- しきい値を上げると、買い系は「勝ち」の条件が厳しくなるため勝率は下がり、
  売り系は「負け」の条件が厳しくなるため勝率（負けない確率）は上がる。
  この理由はguide.htmlのITM日数のしきい値セクションに具体例付きで追記済み
  （9-5参照）。
- 損失額・プレミアムの入力欄は、選んだ「取引の種類」によってラベル・
  有効/無効が変わる（updateRiskRewardInputUI、app.js）。
    プット売り(単体):    株購入価格（旧ラベル「権利行使価格」。権利行使
                          されると実質的に株を購入することになるため、
                          より直感的な名称に変更した。値自体は変更なし）
    ブルプット/ベアコール(スプレッド): 権利行使価格の差額(スプレッド幅)
    コール売り(単体):    損失額(無限大)。理論上損失が無限大になるため
                          入力欄自体を無効化し、損益分岐の判定も
                          「損失無限大のため判定不可」で固定表示。
    プット買い/コール買い(単体)、
    ブルコール/ベアプット(スプレッド・買い): 支払いプレミアム額
                          （これがそのまま実際の最大損失額になる）
  【保留中】ブルコール/ベアプット(デビットスプレッド)の最大損失について、
  ユーザーから「支払いプレミアムではなく権利行使価格の差額（スプレッド幅）
  を使うべきでは」という指摘があったが、標準的なオプション理論では
  デビットスプレッドの最大損失は支払いプレミアム額であり（スプレッド幅は
  むしろ最大利益の計算に関わる数値）、この点をユーザーに確認質問した
  ところ、回答保留のまま次の指示待ちとなっている。この項目を今後触る際は
  必ず先にユーザーの回答を確認すること。安易にスプレッド幅ベースへ変更
  しないこと。

9-2. 2つの母集団・分母の設計（重要な合意事項）
--------------------------------------------------------------------
結果は「絞り込みなし（分析結果と同じ母集団）」「エントリー条件で絞り込み
あり」の2ブロックで表示される。

【重要】「絞り込みあり」側の勝率の分母は、絞り込み前の元の母集団ではなく、
値動き条件に当てはまった日数（該当日数・絞り込み後の件数）を使う。これは
議論の末にユーザーが明確に合意した設計であり、今後変更する場合は必ず
この経緯を踏まえること。

  検討の経緯: 当初ユーザーは「分母は集計期間−判定期間のまま（絞り込みは
  分子だけを絞る）」という案を提示したが、具体例（元の母集団223日、該当
  日数12日、うち負け3日）で試算すると、
    元の母集団223日を分母 → (223−3)÷223 ≒ 98.7%（条件に当てはまらな
      かった211日が薄める形になり、実態より高く見える）
    該当日数12日を分母    → (12−3)÷12 = 75%（実際にエントリーする場面
      だけに絞った、より実態に近い数字）
  という違いが生じることを説明したところ、ユーザーは「条件で絞り込む目的
  は『その条件が出た時だけエントリーする』ことなので、勝率も『その条件が
  出た日の中で』計算するのが実際のトレード判断に対応する」と納得し、
  該当日数を分母とする設計で確定した。この説明はguide.htmlの「エントリー
  条件で絞り込みあり」の分母セクション（id="g-rr-denominator"）にも
  そのまま掲載している。
- 実装: computeConditionalItmAnalysisがitmDaysListを返すよう拡張し、
  その長さ(=matchedCount=該当日数)を分母として使っている。

9-3. 損益分岐との比較・利確割合(%)
--------------------------------------------------------------------
- 売り系: 「一回の損切における上限額」（旧名称「損益分岐の最大許容損失額」。
  「敗率は〇%まで」という表現を追加したのに合わせて改称）
    計算式: 予想利益(利確時) × 勝率 ÷ (1 − 勝率)
  実際の最大損失額がこの上限額以下なら「統計的に有利」、上回れば
  「統計的に不利」のバッジを表示。上限額のすぐ下に「敗率は〇%まで」
  （＝100%−勝率をそのまま表示したもの）を併記。
- 買い系: 「損益分岐に必要な最低利益額(参考)」
    計算式: 支払いプレミアム額 × (1 − 勝率) ÷ 勝率
  買い系は勝ったときの利益額が変動しこのツールでは追跡していないため、
  有利/不利の自動判定は行わず参考値としてのみ表示する（この設計はユーザー
  に提案し明示的に承認を得た）。
- 利確割合(%)（売り系のみ）: 信用売りポジションを満期を待たず反対売買
  （買い戻し）で決済する場合、買い戻しにも費用がかかるため実際の利益は
  受取プレミアムの全額にはならない、というユーザーからの指摘を受けて追加。
    予想利益(利確時) = 受取プレミアム額 × 利確割合
  未入力時は100%（満期まで保有）として計算。上記の「一回の損切における
  上限額」の計算では、受取プレミアムそのものではなくこの予想利益を使う。
  「実際の最大損失額」（満期まで保有した場合の最悪ケース）は利確割合の
  影響を受けない、という点をユーザーに確認の上そのように実装した。
  実装: expectedProfitOnClose（calc.js）。
- 【バグ修正】勝率が100%(サンプル内で一度も負けがない)または0%の場合、
  breakEvenMaxLoss/breakEvenMinGainが0除算を避けるためnullを返す実装に
  なっており、UIが「入力待ち」（未入力扱い）と誤表示する不具合があった。
  100%→Infinity（無限大・統計的に有利）、0%→0（統計的に不利）を返すよう
  修正し、UI側もNumber.isFinite()で「無限大」表示に対応した。

10. ティッカー履歴（入力候補）機能の追加
====================================================================
ティッカー入力欄をクリック/フォーカスすると、過去に分析したティッカーが
プルダウン候補として表示され、選択するか自由に新規入力できる機能。

- 実装は site/js/tickerHistory.js に集約。localStorageキー
  "itm-tool-ticker-history-v1" に、直近使用したティッカーを先頭に最大20件
  保存する（loadTickerHistory/addTickerToHistory）。分析ページ(app.js)・
  詳細マトリクスページ(detail.js)の両方から同じキーを共有しており、
  どちらで分析しても両ページの履歴に反映される。
- 分析が成功する（fetchHistoryが成功する）たびに addTickerToHistory を呼ぶ。
  失敗したティッカーは履歴に残らない。
- 【重要な設計変更】当初はHTML標準の<input list>+<datalist>で実装したが、
  「ティッカーが既に入力済みのタブでクリックすると、現在の値と一致する
  1件しか出てこない」という不具合をユーザーに指摘された。これはdatalistが
  ブラウザ側で現在の入力値によって候補を自動フィルタする仕様のためで、
  HTML標準機能では回避できない。そのため自前のドロップダウン実装
  （setupTickerHistoryDropdown、.ticker-dropdown要素を動的に生成/削除）に
  作り直した。クリック/フォーカス時は入力値に関わらず常に全履歴を表示し、
  入力し始めるとその文字列を含む候補だけに絞り込む。候補クリックで入力欄
  に反映されるだけで、分析は自動実行しない。
  → 教訓: ブラウザ標準のdatalistは「現在の値でフィルタする」という仕様上
    の制約があり、「常に全候補を見せたい」という要件には使えない。
- 【CSSの落とし穴】.field要素にhidden属性を付けて条件表示を切り替えよう
  としたところ、.field{display:flex}という既存ルールが、ブラウザ標準の
  [hidden]{display:none}ルールを上書きしてしまい、hidden=trueにしても
  実際には非表示にならないバグがあった（リスクリワード分析の新規フィールド
  で発見）。.field[hidden]{display:none}という明示的なルールを追加して解決。
  → 教訓: displayを直接指定するクラスに、後からhidden属性で表示制御しよう
    とすると、CSSのカスケードにより無効化されることがある。同様のクラス
    (.summary, .form-row等)にhidden切り替えを追加する際は要注意。
- 共有リンク（後述）にもティッカー履歴を含められるよう拡張済み。

11. リスクリワード分析「損切額から損益分岐を確認」機能の追加
====================================================================
既存の「絞り込みなし/絞り込みあり」（過去の実績データに基づく勝率）とは
性質が異なる、第3のブロックを追加した。自分で決めた損切額（買い系は
見越し最大利益額も）だけから、期待値がちょうどゼロになる「損益分岐勝率」
を算出し、それを実績勝率と比較する機能。

--------------------------------------------------------------------
11-1. 「絞り込みなし/あり」との違い（重要な設計思想）
--------------------------------------------------------------------
- 「絞り込みなし/あり」の勝率　→　過去の実績データから計算した「実際の勝率」
- 「損切額から損益分岐を確認」の損益分岐勝率　→　実績データを一切使わず、
  入力した損切額（・見越し最大利益額）という数字だけから算数的に逆算した
  「割に合うために必要な勝率」
  計算式: 損益分岐勝率 = 損切額 ÷（利益額 ＋ 損切額）
  （売り系の利益額=予想利益(利確時)、買い系の利益額=見越し最大利益額）
これは「一回の損切における上限額」（勝率→許容損失額を逆算する式）の逆で、
損切額→必要勝率を逆算したもの。同じ損益分岐のラインを逆向きから見ている。
実績データを使わないため、母集団（絞り込みなし/あり）には依存せず、値は
1つだけ算出される。算出した損益分岐勝率を、上にある2つの「実際の勝率」
それぞれと比較し、実績勝率が上回っていれば「統計的に有利」と判定する
（同じ損益分岐勝率でも、どちらの母集団と比較するかで判定が変わり得る）。

--------------------------------------------------------------------
11-2. 入力欄・上限クランプの挙動
--------------------------------------------------------------------
- 売り系（コール売り単体を含む全4種）: 損切額を入力。コール売り単体以外は
  実際の最大損失額を上限、コール売り単体は損失無限大のため上限なし。
- 買い系（全4種）: 見越し最大利益額と損切額を入力。損切額は支払いプレミアム
  額を上限。ブルコール/ベアプットは見越し最大利益額の上限（スプレッド幅−
  プレミアム）を計算するため、新規に「権利行使価格の差額(スプレッド幅)」
  入力欄を追加（既存の実際の最大損失額＝支払いプレミアム額の計算式は
  変更していない。あくまで上限チェック専用）。
- 上限を超える入力をした場合の挙動をユーザーと相談し、C+A方式で確定:
  入力中はそのまま自由に打たせ、フィールドからフォーカスが外れた瞬間だけ
  上限値にクランプし、理由を示す警告文（「上限(◯◯)を超えていたため、
  ◯◯に調整しました」）を表示する。input(debounce)イベントでは丸めない、
  blurイベント専用でクランプする、という役割分担がポイント。
- 【重要】コール売り単体（従来「損失無限大のため判定不可」で受取プレミアム
  ・利確割合の入力欄も無効化されていた）でも、この新機能では予想利益
  （受取プレミアム×利確割合）を使うため、これらの入力欄を再度編集可能に
  変更した（updateRiskRewardInputUIのelse.rrPremiumInput.disabled等）。
  無限大損失のため「一回の損切における上限額」側の判定は従来通り不可の
  ままだが、「損切額から損益分岐を確認」側では機能する、という使い分け。
- 反対売買（早期決済）の指値への換算式もクリック説明・guide.htmlに追加:
    売り系: 指値 = 約定レート（受取プレミアム額）＋ 損切額
    買い系: 指値 = 約定レート（支払いプレミアム額）− 損切額

11-3. 実装
--------------------------------------------------------------------
- calc.js: breakEvenWinRateFromLoss(gain, loss) = loss/(gain+loss)。
- app.js: renderCutLossSection()が新設の入力欄・結果を描画。
  computeCutLossCaps(t)で上限を計算し、blurハンドラ(onCutLossBlur/
  onExpectedGainBlur)でクランプ処理を行う。
- 勝率は「10回換算で◯勝☆敗」の表現で表示（tenTrialText()、既存の説明文
  「勝率84%なら10回中8.4回勝って1.6回負ける」という表現と統一）。

14. 開発・デプロイの運用フロー
====================================================================
  1. site配下のファイルを編集
  2. Claude Codeのpreview_start（.claude/launch.json の "itm-tool"）で
     ローカル確認。javascript_toolでツールチップのtitle属性やクラス名を
     直接検証するなど、視覚だけでなく数値レベルで確認してきた。
  3. git add → git commit（Co-Authored-By行つき）→ git push origin main
  4. Cloudflare Pagesが自動ビルド・デプロイ（数十秒〜1分程度。時々1分以上
     かかることもあるので、反映確認のcurlポーリングは十分な回数/間隔で）。
     curlでjsファイルの中身をポーリングして反映を確認する方法が確実
     （例: curl -sL https://itm-bunseki.pages.dev/js/detail.js | grep 目印。
     Cloudflare Pagesは拡張子なしURLへの308リダイレクトを返すことがある
     ため、curlには必ず -L を付けること）。
  5. 本番URLを新規タブで開いて最終確認。
     【注意】同一タブのリロードやCloudflare Pages自体のキャッシュにより、
     既存タブでは更新後も古いコードが表示され続けることがある。検証は
     必ず新しいタブで行うこと（これは今回の作業中に何度も踏んだ落とし穴）。
